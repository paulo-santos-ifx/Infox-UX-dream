# Critical Code Review Skill

A rigorous code review skill designed to combat AI bias and eliminate technical debt at the source.

## Philosophy

When an AI generates code and then reviews it, there's a cognitive bias: **the code defends itself**.

This skill reframes the reviewer as an **auditor and skeptic**, not a defender. The reviewer acts as if they **did not write the code** and assumes worst intentions.

Think of it as the rabid senior engineer reviewing a risky PR at 2 AM, not the code author making excuses.

## When to Use

Use this skill when:
- ✅ Reviewing code generated by AI agents
- ✅ Reviewing refactored code for architectural quality
- ✅ Examining pull requests that touch core systems
- ✅ Looking for technical debt before it calcifies
- ✅ Validating SOLID principles adherence

## How It Works

The skill follows an 8-step pipeline:
1. **Context Understanding** — Read refactor context to understand _why_
2. **Change Inspection** — Analyze _what_ actually changed
3. **Architectural Review** — Evaluate system-level impact
4. **Code Quality Review** — Identify code smells
5. **Maintainability Review** — Will this age well?
6. **Risk Analysis** — What can break?
7. **Performance Check** — Hidden performance debt?
8. **Improvement Suggestions** — What should change?

Each step is independent but builds on previous context.

## Output

Reviews generate a structured report:

```markdown
# Code Review Report

## Context

[What was being done]

## Architecture

[System-level assessment]

## Code Quality

[Specific issues found]

## Maintainability

[Long-term concerns]

## Risk Analysis

[Potential breaking changes]

## Performance

[Performance concerns if any]

## Improvement Suggestions

1. [Specific action]
2. [Specific action]

## Summary

[Overall verdict]
```

## Severity Levels

Each finding is classified:
- 🔴 **CRITICAL** — Must fix before merge
- 🟠 **HIGH** — Should fix soon
- 🟡 **MEDIUM** — Consider improving
- 🟢 **LOW** — Nice to have

## Integration with large-scale-refactor

When used together, these skills create a powerful feedback loop:

```
Refactor Agent
    ↓ generates changes
Review Agent
    ↓ identifies issues
Refactor Agent
    ↓ improves based on feedback
Review Agent
    ↓ final validation
Complete
```

This prevents AI-generated technical debt from accumulating.

## Example Usage

### Scenario 1: Consolidating Components

After running the `large-scale-refactor` skill to merge 3 Button implementations:

```
1. Refactor agent consolidates into components/Button/Button.tsx
2. Review agent checks the new component for:
   - Dynamic Tailwind class safety
   - TypeScript coverage
   - Theme abstraction needs
   - Performance implications
3. Refactor agent addresses HIGH priority issues
4. Review agent does final check
```

### Scenario 2: Extracting Repository Layer

After running refactors to separate persistence:

```
1. Refactor agent creates repositories/UserRepository.ts
2. Review agent verifies:
   - Error handling and error type boundaries
   - Pagination support
   - Query efficiency (N+1 patterns)
   - Type safety
   - Audit trail capability (timestamps)
3. Issues get logged
4. Refactor agent improves
5. Final review passes
```

## Key Principles

### 1. Assume Nothing

Don't assume the code is correct. Challenge every assumption.

```
❌ "This looks fine to me"
✅ "This scales to 1M records? How?"
```

### 2. Be Specific

Generic criticism is noise. Specific feedback is actionable.

```
❌ "This is complex"
✅ "renderButton() has 45 lines. Extract styling into separate concern."
```

### 3. The 3-Year Test

Ask: "If this lives in production for 3 years unchanged, will future devs hate it?"

### 4. Don't Defend

Never let existing bad code justify new bad code.

```
❌ "Component X does this too"
✅ "Component X has the same issue. Let's fix both."
```

## Anti-Patterns

### Defending Your Own Code

❌ Don't be the code's lawyer:
```
"The code is fine because I carefully considered..."
```

✅ Be the skeptic:
```
"This breaks for 1M records. How do we scale?"
```

### Vague Criticism

❌ Don't do this:
```
"This could be better"
```

✅ Do this:
```
"Function has 3 return statements in nested conditionals.
Suggestion: Refactor to early returns or extract into switch statement."
```

### Missing Context

❌ Don't review without understanding _why_:
```
// Just started reviewing code
```

✅ Read the context first:
```
# Read .refactor/task.md
# Understand objective
# Then review with context
```

```bash

node scripts/review.js --init

# Analyze code complexity
node scripts/analyze-complexity.js src/

# Run full review
node scripts/review.js

# Validate review meets standards
node scripts/validate-review.js .refactor/review.md
```
